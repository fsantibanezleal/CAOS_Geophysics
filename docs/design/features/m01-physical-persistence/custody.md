# Exact proposed custody inventories and accounting: milestone A

Status: review candidate, no runtime proof. This registry is separate from [publication targets](sql-contract.md#7-physical_publication_intents-and-physical_publication_targets). No caller supplies a file path. No physical file is admitted on filename alone. All filesystem guarantees require future platform tests and milestone B's exclusion protocol.

## 1. Complete control JSON

Proposed sealed inventory schema `geophysics.physical-custody/v1` has EXACT keys: schema,batch_id,owner_id,project_id,origin_kind,origin_id,stage_id,deletion_receipt_id,raw_asset_id,raw_sha256,raw_bytes,parser_version,method_id,capacity_bytes,initial_files,removed_ordinals. Types equal the SQL domains, including named nullable stage/receipt/raw/parser/method fields and exact origin/capacity conditions. All keys required; no extra keys. initial_files is sorted by ordinal, contains 0..4096 entries, has unique ordinal/location/leaf, and is IMMUTABLE after seal. Each entry has EXACT keys ordinal,role,location,artifact_id,leaf,max_bytes,actual_bytes,actual_sha256, with SQL types; all measurements non-null. removed_ordinals is the sorted unique subset of those ordinals with verified removal. No mutable state field enters this sealed inventory; SQL batch/file state and retained charge must agree with it.

Inventory bytes are saved canonical application JSON (sorted compact UTF-8 ensure_ascii=False, allow_nan=False); inventory_sha256 is SHA-256 of those exact bytes. Complete inventory<=4 MiB, each entry<=1024 source bytes, depth<=8, nodes<=100000, keys<=64 UTF-8 bytes, strings<=180 UTF-8 bytes, integer lexical/domain checks as in protected contract. Before seal, rows are bounded declarations with unknown measurements NULL; root/job stages are charged at FULL capacity (deletion preparation keeps original committed row charges until atomic transfer). No fabricated inventory or hash. Stage declarations<=64, deletion declarations<=4096. Seal compares the ENTIRE ordinary-file/directory inventory, not a successful subset. Rehashing names/bytes cannot authorize an unregistered location/role or foreign artifact.

Initial measured entries stay in inventory after removal. Updating removed_ordinals/inventory hash and retained charge is one transaction. This preserves original measurements and permits a fresh recovery reader to detect partial cleanup. At seal, initial_files contains every actual present file; declared but never-created optional slots are deleted in that seal transaction only after complete namespace verification. There is no invented zero-byte file for an unused declaration. The inventory has no self-digest. SQL row dumps are not this wire schema. Unknown/missing/duplicate fields, future roles or mismatched rows close admission. Neither an arbitrary user path nor a recursively discovered cache name may become a declaration after failure.

## 2. Namespace and role registry

Server-selected stage UUID is fresh; job_stage stage_id=job_id, root_stage stage_id=reserved root UUID. Root-stage raw/parser evidence is committed before structural parsing; the family slot is allocated with the prepared root intent after parsing, when exact target bytes exist. Competing parses may have separate charged stages but cannot reserve/publish two raw/parser families. Stage directory is `.job-staging/{stage_id}`. Publication destination keys use the exact current derived layout. Deletion uses existing `.deleting/{owner}--{project}` and `.deleting/{owner}--{project}--derived` roots; no additional provider/root is invented.

The above completion-file content is EXACT proposed schema `geophysics.physical-child-complete/v1`: schema,job_id,method_id,scientific_output_bytes,scientific_output_sha256. Job ID/method bind control, bytes positive within that method's scientific-output cap, SHA binds exact scientific.json bytes. Root parsing has no child completion file. It is written/fsynced LAST; EOF/schema/hash checks are required, and it is not proof of CPU telemetry, numerical accuracy or publication. Missing marker means no publishable child result.

Cache support is CLOSED unless the fixed module manifest and actual dependency tests establish these literal slots with no extra files. This is a proposed wrapper-owned cache namespace, NOT a claim existing Harmonica/Numba libraries write these names. If real dependencies require another namespace, obtain a separately reviewed exact registry before admission; do not disable/change numerical algorithms, rename discovered files or relax the grammar silently. Empty reviewed cache inventory is allowed if actual runner proves no filesystem cache output. Capacity does not grant permission to unknown names.

leaf means a fixed name/registered relative key, not any T(180) string. pending_target requires exact owner/project/artifact-derived key; deleting_derived permits ONLY the two listed two-component forms; deleting_raw one UUID; stage only table literals. Resolve from the owning batch, never concatenate a user path. Necessary directories are exactly these fixed namespace parents. Reject symlink/junction/reparse/hardlink/reflink aliases and nested/unexpected directories; require ordinary nlink=1 files and reviewed exclusive handle/directory checks. A stat/hash followed by a raceable unlink is NOT sufficient proof. Platform-safe no-follow/removal and directory-sync behavior belongs to B's measured platform subdesign.

Pending targets of a prepared intent are charged through its permanent reservation and have target records, NOT duplicate charged custody rows. On proven abandonment only, copy their EXACT target identity into publication_abandon custody rows and atomically replace that reservation with actual target charge. On success they become committed dataset/result bytes, not cleanup targets. Stage dataset/result copies remain distinct custody entries and remain charged after success. Never unlink a committed destination to clean its stage copy.

## 3. Reservations and exact charge equation

All amounts are logical retained source bytes, not claims about filesystem block allocation, SQLite WAL/page size or physical media erasure. Identical hashes do not deduplicate different files. Each copy is separately charged. Rename transfers one file's custody/charge without creating a second byte copy. Temporary hardlink/reflink aliases are UNSUPPORTED; no zero-cost link exception. Global actual disk/headroom remains independently measured, including SQLite pages, WAL, exports and other processes.

Account private admission charge is EXACTLY:

`sum(committed raw byte_count) + sum(committed dataset byte_count) + sum(succeeded result_bytes) + sum(physical control charge) + sum(unconsumed permanent reservations) + sum(custody batch charged_bytes) + unchanged registered legacy active-method reservations`.

AccountUsage.raw_bytes remains the first term ONLY. Registered legacy methods are gravity.station-outlier-flags/v1, mt.edi-full-tensor-qc/v1, mt.edi-fixed-thickness-trf/v1 with their unchanged per-method reservation constants; an unknown physical/future method has no legacy flag fallback. Legacy constants come from pinned processing_contract/mt_contract, not guessed numbers here. Exports retain existing separate guards; their durability/global quota semantics must be covered by B's writer inventory before physical admission, not claimed solved by this equation.

Physical control charge is the SUM of length(request_bytes), length(module_manifest_bytes), length(parent_production_bytes if non-null), exact stored UTF-8 bytes of processing_jobs.request_json and preflight, and length(adapter_receipt_bytes if present). This explicitly charges preserved duplicates, including SQLite JSON serialization overhead. Query stored text octet length, not Python character count or a reserialized object. Control charge persists for terminal jobs while rows exist. It is reserved atomically when queue/control rows are inserted; no unbounded history exemption. Other bounded scalar/control/index/page overhead is addressed by measured DB/global capacity, not falsely equated with this byte sum. Total DB/WAL growth needs actual B/resource tests before production admission.

Root stage capacity is 32 MiB, correction256 MiB, transform512 MiB. Before any file create/write, batch reserved/active charged_bytes=capacity and all allowed file slots are declared; each file and the entire stage must stay within their respective caps. Sum of individual maximums is NOT permission to exceed total capacity. No shared inherited worker scratch estimate substitutes for a per-stage ledger. Queued job simultaneously reserves permanent ceiling80/128 MiB plus stage256/512 MiB and control charge. Root parsing initially reserves32 MiB stage; preparing its root intent adds16 MiB permanent reservation under quota before any destination copy. Sum unconsumed permanent reservations includes root-intent reservations AND job-control reservations; job intents carry0 to prevent duplicate charge. This conservative reservation can legitimately reject a job under the current1-GiB account quota. Do not weaken quota because configured maximums do not fit.

At seal, measure every exact owned file hash/count after the child is reaped/no writer remains; save immutable inventory and replace full capacity charge with actual retained sum in ONE DB transaction. This is allowed only with complete exact inventory and durability proof, never while files can grow. If an unknown/oversize file is found, keep quarantine/full capacity or measured larger charge and close admission. At final success commit, permanent reservation becomes committed actual dataset+result bytes; stage actual charge remains cleanup_pending. Unused permanent capacity is released; its pending installed files are NOT simultaneously charged again. At terminal failure/cancel/abandon, all stage and pending-target actual retained charges move to cleanup_pending; no child/result is visible, all abandoned output targets remain charged. If exact inventory cannot be sealed, keep existing reservation/quarantine and do not retire evidence.

## 4. Transition table

| Event | Must exist before filesystem action | Required atomic DB effects |
| --- | --- | --- |
| Queue / root parse reservation | Owner/project/raw/input checked, no files yet | Insert batch/slots and control/permanent reservation; enforce quota; then create stage |
| Child complete | Exclusive closed exact stage, actual measurements | Seal inventory and charge actual retained bytes; running job unchanged |
| Prepare publication | Complete bounded outputs; no destination yet | Allocate family ordinal, prepared intent and exact targets; retain stage and permanent charge |
| Install copy | Committed prepared intent/reservation | Exclusive destination copy within permanent cap; fsync under reviewed platform protocol; no success visibility |
| Success | All destinations verified, cancellation absent | Insert dataset/edge/producer/result, terminal succeeded, allocator counts; permanent->committed; stage->cleanup_pending; delete targets then intent; ALL same commit |
| Failure/cancel/abandon | Full child-tree reap; exact retained inventory | Terminal nonsuccess and no outputs; stage and pending targets->durable cleanup debt; release only proven unused capacity; delete targets/intent and decrement reserved count in SAME commit |
| Project deletion | Exact complete declaration and durable batch; no active jobs | Receipt + custody/charge + logical deletion + raw/derived/control accounting transfer co-commit; debt has no project/intent FK |
| Partial cleanup | Each exact owned file verified under exclusion | After durable removal, add ordinal to removed list, state removed, charge retained sum; commit; never release on attempted cleanup |
| All cleanup complete | Complete removed set and empty exact owned namespace proven | state removed,charge0,removed_us measured; preserve inventory/evidence; no success rewriting |

For project deletion, before moving any file retain its existing committed charge; batch may be reserved with charge0 only as a SPECIAL deletion preparation, therefore the generic reserved=capacity SQL rule must NOT be used for this origin. Proposed exact exception: project_deletion reserved/active has charge0 and all committed bytes remain charged by original rows; its capacity is the exact verified original inventory sum (minimum1 for empty project control identity). Final deletion commit replaces committed file charges with actual retained custody charge, not both and not neither. Deleting logical DB controls releases their logical charge, not proof SQLite pages/WAL/media were erased; global retained DB capacity remains independently measured. A second deletion copy, if ever needed, is forbidden here; rename only. Before commit, recovery must classify moved files without deleting them or releasing original row charges. Inventory for exact moved stages/control spools can coexist as separate batches but NEVER be charged twice; active root stages and unresolved stage debt block deletion until reviewed reconciliation.

An unlink crash before charge-update leaves conservative overcharge and retained evidence. Recovery may mark an absent file removed only after proving its exact registered file was durably removed and no renamed/alias/unknown copy exists; ordinary absence alone is not blanket cleanup authority. Any uncertain DB commit enters B classification; stale ORM/session state cannot decide whether installed copies are committed or abandoned. No class of file is cleaned through a recursive glob.
