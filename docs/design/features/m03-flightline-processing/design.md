# M03 mapped flight-line processing design

Date: 2026-10-25. Basis: approved product SDD section 4, the source-specific [Charleston intake research](../../../research/m03-charleston-flightline-research-2026-10-25.md), and the USGS provider record. This local vertical is a component of M03, not full method acceptance.

## Scope and data semantics

`data-pipeline/magnetic_processing.py` accepts a bounded CSV through an explicit user field map or the closed JSON request contract. It requires projected coordinates in metres, a declared CRS, a source SHA-256, citation, rights decision, processing-state description, value unit and sensor-height field. It does not infer columns, unit, CRS or correction history. The CSV adapter calculates SHA-256 over the input bytes and preserves the mapped observations as rows; unmapped columns remain in the source file and are not interpreted. The JSON entry point validates the declared digest's syntax but cannot prove that it is the digest of a separate original file, so its receipt explicitly leaves source-byte recomputation false.

The processor reports line sample counts, coordinate extents, line-centre spacing estimate and per-line height ranges/median/MAD. Height outliers are flagged beyond six scaled MAD; when MAD is zero, any nonzero deviation is flagged. These are screening flags, not instrument tolerance or a calibrated error model. Flagged observations remain in the input; none are deleted or corrected. Exact collocated values from distinct lines are summarized separately from geometric segment crossovers. The input contract requires a distinct acquisition-order value for each line sample. At each non-collinear segment intersection the processor linearly interpolates each line's recorded field and reports the signed difference and aggregate residuals; this diagnostic does not estimate or apply tie-line leveling.

## Split, interpolation and grid

The split unit is a whole flight line. Line centres are projected onto the estimated survey-normal axis, sorted, then a deterministic contiguous interior block is held out with a stable seed. At least two flight lines remain for fitting. Tie lines are retained for geometry/height reporting and excluded from fit. This supports a spatial prediction question without randomly scattering neighboring samples across fit and test.

Piecewise-linear Delaunay interpolation is fit to flight-line samples only. Grid spacing is an explicit metre parameter; output contains x/y physical axes, values and a separate support mask. Unsupported cells are encoded as zero only alongside a false mask. Grid values interpolate observations at their recorded sensor heights; they are not continued or corrected to a common elevation. Whole-line holdout predictions use the same interpolation without refitting. MAE/RMSE are reported only on supported held-out samples, with support count and coverage fraction. This is interpolation validation, not an inverse, geology estimate or comparison against a provider grid.

## Boundaries

No diurnal/IGRF/lag/height correction, line levelling, tie-line adjustment, regional removal or provider-grid comparison is implemented by this vertical. The authenticated project path accepts source-bound magnetic CSV declarations; its workbench exposes mapping, CRS, original hash, citation and processing state. The authenticated worker now re-verifies the original, runs the exact local M03 implementation in a bounded child process, stores a typed result and exports a rights/provenance-bound ZIP with nT/m units. Integration tests execute the child through the real API worker and verify the held-out interpolation and export on an authored planar control. Online job admission remains disabled by default until actual ML VPS resource admission is measured and reviewed; a locally enabled test is not host acceptance. The Charleston deliverable is already-processed horizontal magnetic gradiometry; its matching dictionary/report/data have not been acquired in this environment. Do not use the authored control to claim Charleston validation.

The local CSV adapter allows up to 256 MiB; the authenticated upload path allows 50 MiB. Online processing bounds observations and grid cells to 250,000, result members to 64 MiB, scratch to 256 MiB, memory to 2 GiB and wall time to 600 s. Admission estimates memory as 512 MiB plus 4 KiB per source row and reserves the method scratch allowance against the account quota. The worker polls RSS, scratch, wall time and owner cancellation, then checks result identity, engine hash and bundle structure before commit. These are implemented controls, not measured VPS capacity evidence. SciPy `LinearNDInterpolator` and NumPy perform the numerical work. Actual VPS timing, memory, cancellation and browser result parity remain unaccepted. The source catalogue's estimated 2.58 GB CSV is outside this bounded online contract.

The public `?instrument=magnetic-local` workbench executes the same `data-pipeline/magnetic_processing.py` implementation locally in a Web Worker through version-pinned Pyodide, NumPy and SciPy. The survey CSV stays in the browser; the initial numerical runtime and packages are fetched from a pinned CDN and cached by the browser. First use downloads approximately 54 MiB. The browser path is bounded to 16 MiB per CSV, 25,000 rows, 100,000 grid cells, 2,000,000 crossover segment pairs and 180 seconds, and supports cancellation. Its explicit mapping, units, projected CRS and provenance fields feed the canonical adapter. It exposes line extents and height QC, interpolated crossovers, support-masked Delaunay interpolation, whole-line holdout coverage/errors, limitations and a JSON result export. This is local processing for a user's eligible CSV, not a provider-data acceptance claim.

Parity evidence currently covers one deterministic controlled fixture, including output arrays, masks, scores, provenance and engine digest. The browser runtime uses Python 3.13.2 / NumPy 2.2.5 / SciPy 1.14.1 while the native tested environment uses Python 3.12.10 / NumPy 2.2.6 / SciPy 1.15.2. Exact fixture parity does not establish parity for arbitrary CSVs, degenerate geometries, browsers or device memory/latency. Broader randomized and adversarial parity, supported-device resource measurements, accessibility/interaction acceptance and actual Charleston source evidence remain release gates.

## Verification target

The method gate includes an analytic planar-field holdout control, deterministic split, height-outlier retention, duplicate-training-coordinate rejection, metric-coordinate rejection and explicit-mapping CSV import. These establish implementation behavior on authored controls only. The SDD's full M03 acceptance still additionally requires the acquired provider dictionary/report/CSV/grid, measured flight/tie crossover and height diagnostics, provider processing lineage, a source-specific blocked-line holdout, justified gridding and continuation controls, and a rights/provenance-bound case artifact.
