# Exact proposed M01 physical vertical contracts

Status: planned, no API or wire contract activated. These definitions are review candidates, not existing endpoints or exported artifacts. Baseline and approval boundary: [design](design.md). Every object below rejects missing/extra keys unless an optional key is explicitly listed; arrays retain station order. Version suffixes are schema/method identities, not dataset parser hacks. UUIDs are server-owned canonical UUID strings, hashes lowercase 64-hex SHA-256, bytes/ordinals/counts exact integers, finite numbers never booleans or numeric strings. Null is allowed only where named.

Corrected registry proposals below enumerate parent_production, physical list receipts, bundle nested lineage/digest declarations and complete APPLICATION envelope budgets. These are NOT main-approved or activated. Large SQL/custody/intent/tombstone/authority/source-bundle contracts/types/caps remain explicitly NOT_SET in migration/recovery; implementation stays blocked, no inference/truncation or generic JSON fallback. Scientific-inner caps alone are insufficient. Preserve all legacy v1 guards unchanged.

## 1. JSON and upload boundary

Reuse the existing authenticated project raw-upload route, filename handling, streamed actual-byte count/hash, quota, CSRF, source permission and immutable SourceRecord/RawAsset. Add a reviewed discriminator `gravity_stations_json` with application/json MIME and an explicit physical-schema mode. Do not pass it through generic projected-CSV PhysicalInput or assign an unavailable measurement epoch/frame/datum default. SourceInput fields and private-storage attestation remain the existing source contract; dataset source_citation/rights remain supplied scientific statements. Retain both; inconsistency is a declared review reason, not an invented overwrite. A private storage permission does not authorize public redistribution.

The raw JSON document is exactly the scientific dataset itself, not `{dataset,config}`, an adapter request or an app envelope. No compressed uploads, executable references, ndarray/object arrays, CSV auto-conversion or external URL dereference. Proposed raw cap 16 MiB actual bytes. Scientific payload's ASCII-escaped canonical form is capped at 8 MiB for roots; complete adapter/transform requests are capped at 16 MiB when submitted. A raw file fitting its transport cap can still be structurally rejected; no silent subset/normalization.

Strict parsing occurs BEFORE framework coercion/default JSON decoding can discard duplicate names. Count actual received bytes (sentinel read), structural depth outside quoted/escaped strings, token length and total tokens/nodes before allocating the final object. Depth is at most 16 for complete scientific child request (root depth 1), nodes at most 200000 counting containers/keys/scalars, string values at most 8192 UTF-8 bytes, keys at most 128 bytes, numeric lexemes at most 128 ASCII characters and integral magnitude at most 2^53-1 for browser-safe exact integers. This is a stricter online structural lane than the offline core, not a rewrite of its input numbers. Shifted envelope depth is included when checking job feasibility. Reject malformed/trailing JSON, BOM/invalid UTF-8, lone surrogates, decoded-key duplicates including escape-equivalent names, nonfinite constants, parse_float overflow (`1e400`), excessive integer digits, mixed/unknown keys and bool numeric values. Cap multipart metadata at its existing 16-KiB limit; the uploaded file is a separately bounded part. Job JSON has a dedicated 16-MiB scientific parameters cap plus a bounded identity envelope, not an unlimited request-body middleware bypass.

Root structural validation knows exact types/key sets/literal declarations/scalar ranges/array lengths/history-record shapes and exact duplicate station IDs. It does NOT calculate converted gravity, wrap longitude to detect physical coordinate equivalence, convert heights, replay history, derive uncertainty, project geographic coordinates, test rank/covariance PSD or verify field/provider bytes. Those numerical admissions occur in the child. A structurally accepted root's verdict is `structural_only`; do not label it scientifically validated. Invalid inputs retain existing permitted raw-storage semantics and a safe rejection; they never gain a fabricated eligible dataset.

Integral fields use token-aware source validation BEFORE numeric coercion: JSON integer lexeme -?(0|[1-9][0-9]*) only, then field-specific sign/range <=2^53-1. Reject 1.0/1e0 as ordinals/counts/seeds/bytes even when numerically integral; reject booleans/strings and leading zeros. Scientific finite-number fields may contain valid integer/fraction/exponent lexemes, preserving native int versus float and original source bytes. Browser parsing must retain token classification and must not infer Python scientific digest equivalence from a coerced Number. Required numeric lexeme cap128 bytes, overflow/nonfinite rejection and duplicate-aware source scan remain in force across COMPLETE wrapped objects, not only inner payload.

## 2. Unchanged gravity-stations-1

Required top-level keys: `schema_version=gravity-stations-1`, `metadata`, `state`, `stations`, `history`. State literals: observed_absolute/gravity_disturbance/bouguer_disturbance/terrain_adjusted_disturbance. History lengths corresponding to these states: 0/2/3/4. Correction child retains the exact parent object and its integer/float representation; server never rewrites current values to help history verification.

Metadata required keys: source_kind, source_sha256, source_citation, rights, crs, reference_ellipsoid, height_datum, height_unit, height_sign, gravity_unit, gravity_sign, gravity_quantity, gravity_datum, tide_system, instrument_processing. Optional geoid_model exists ONLY for orthometric heights and is required there. Nonblank text, exact known literals: source_kind field/synthetic_control; crs EPSG:4326; reference_ellipsoid WGS84; height_datum ellipsoidal/orthometric; height_unit m; height_sign upward; gravity_unit mGal/m/s^2/microGal; gravity_sign downward/upward; gravity_quantity absolute_gravity; tide_system tide_free. gravity_datum/citation/rights are supplied statements, not automatically verified identities. instrument_processing is exactly calibration/drift/tide, each exactly status/citation. Status applied/not_applicable; calibration must be applied. No unknown or pending instrument reduction is guessed.

Each of 1..400 stations has exactly station_id, latitude_deg, longitude_deg, receiver_height_m, surface_height_m, original_value, value_mgal, gravity_sigma, receiver_sigma_m, surface_sigma_m, latitude_sigma_deg. For orthometric height only, require geoid_m/geoid_sigma_m; forbid them for ellipsoidal height. Latitude [-90,90], longitude [-180,180]; finite declared heights/values; primitive errors finite >=0 in declared units. Original gravity error is in metadata.gravity_unit; current derived uncertainty comes from processing, not replacing the primitive gravity_sigma. No mask, metric XY, job or owner fields.

Each history entry is exactly name, parameters, additions_mgal, input_values_sha256, output_values_sha256. Names are the known ordered normal_reference/elevation_reference/bouguer_plate/terrain_residual prefix. Parameters are the corresponding current core's exact reference/height/plate/terrain contract, not arbitrary JSON. Arrays have original station count. Numeric reconstruction and prior-parameter consistency remain child checks. The raw object is unchanged even when its later scientific job rejects duplicate physical positions, invalid land heights or unreconstructable history.

Correction config requires target and uncertainty_model. Optional density_kg_m3, density_sigma_kg_m3, outlier_z, terrain are precisely core inputs. target must be one of the three derived states, uncertainty_model independent_first_order/conservative_marginals; density 1..10000 kg/m^3, density SD 0..10000 kg/m^3, outlier_z >=1. Plate/terrain require explicit density AND its SD. The following terrain compatibility is the unchanged core contract, not a global permission for nullable numeric inputs:

| Target | terrain omitted | terrain explicitly null | terrain supplied object |
| --- | --- | --- | --- |
| gravity_disturbance | Valid | Valid | Reject |
| bouguer_disturbance | Valid | Valid | Reject |
| terrain_adjusted_disturbance | Reject | Reject | Required exact terrain object below |

Reject non-object/non-null terrain values for every target; an empty or malformed object does not satisfy the terrain target. Compatibility here does not waive target/current-state, history, runtime or error-model admission. Target/current-state relationship is child-authoritative; structural impossible repeat/backward requests can be reported without replay. Null density/error/outlier values remain invalid; no zero substitution.

Preserve the submitted object's exact key presence: a non-terrain config with terrain omitted and the otherwise identical config with terrain:null are both valid but have DIFFERENT submitted_parameters_sha256 (application domain), submitted_config_sha256 (scientific domain), complete six-key scientific_request_sha256 and server-bound request identities. Never delete a submitted null key, insert defaults or normalize before those hashes or idempotency. The core's separately recorded normalized six-key config contains terrain:null for both cases and may have equal normalized_config_sha256 and equal deterministic core results; that does not make the submitted requests identical. No numeric/lexical parent rewriting is allowed.

Terrain is exactly kind=additive_residual_to_plate, unit=mGal, height_reference=WGS84_ellipsoid, density_kg_m3, source_sha256, method, station_ids, additions_mgal, sigma_mgal. Station order/count matches the parent; sigma>=0. Its sign, density equality, error-model compatibility and scientific lineage are checked by the child. No terrain download/calculation service.

## 3. Identity domains

| Identity | Exact input / rule |
| --- | --- |
| raw_sha256/raw_bytes | Exact uploaded original bytes, independent of JSON formatting. |
| supplied_source_sha256 | Unchanged dataset.metadata.source_sha256; supplied provenance, NOT assumed equal to raw hash. |
| dataset_sha256 | Exact stored application envelope bytes. |

Application canonicalization retains existing sorted-key compact `ensure_ascii=False`, `allow_nan=False`, UTF-8 semantics. It is NOT RFC JCS and NOT interchangeable with scientific digest. Name the digest domain in each field. Unicode and int-versus-float golden vectors are mandatory. JavaScript JSON.parse/stringify loses some Python numeric lexical distinctions; browser bundle verification hashes original member bytes and binds declared scientific digests, not a false claim of recomputing Python scientific hashes with JSON.stringify. The API/worker/offline verifier can recompute the existing scientific digests with the exact preserved native representation, using standard library hashing/serialization only.
