# Single-origin service release design

## Scope and inputs

The existing static-only uploader cannot publish the approved private-state API or processing worker. The replacement is one immutable release with `web/`, `source/`, an independently installed API-only `.venv/`, and a hash manifest. Nginx exposes only `web/`. Source includes committed `app/`, required standalone `data-pipeline/` scripts, the cheap source/release guards and their evidence dependencies, and the pinned API requirements. No training runtime, local virtual environment, credential or private original is copied. Runtime installation consumes the pinned API requirements only, not the GPU stack.

`scripts/prepare_service_release.py` takes explicit source/build/output paths. It reads the source revision and tracked path list from Git, checks a clean source, invokes the existing structural convergence and single-origin guards before any output creation, hashes bounded inputs, then creates a new release directory exclusively. It neither obtains authority from a boolean supplied by a caller nor turns component tests into full acceptance. A manifest names the exact source revision, web members, runtime members, bytes and SHA-256. Bounds are16,384 files/32,768 entries,512MiB per file and4GiB cumulative; chunks are65,536 bytes. Destination free space must cover inventoried bytes plus the4MiB manifest bound before output creation. This check cannot reserve space against concurrent writers; a later disk-full failure is retained. Rehash after copying. Reject symlink/reparse ancestors and unsafe relative paths. Trusted operator-controlled input directories remain a precondition; ordinary stat/hash checks are not a hostile same-user race sandbox.

Preparation and isolated qualification are not publication. Requiring final HTTPS/rollback acceptance before any qualification bundle exists is circular: those gates require an actual candidate to test. Preparation therefore validates and preserves the unresolved ledger rather than converting it to accepted. Production activation requires every scientific/UI/data/learned requirement R-001 through R-016 and R-019 to pass their existing measured receipts, plus independently reviewed actual-host candidate jobs/capacity/ownership. R-017 final external HTTPS/browser/rollback gates run after the qualified activation, with the old release retained; R-018 records the resulting complete ledger. Failed final verification restores the old release and never reports acceptance. This sequencing changes no scientific threshold and grants no general gate bypass.

## Stable private state and socket

### Executable runtime staging

`scripts/stage_service_runtime.py` is the Linux-only operator implementation of the API-only installation step. Its CLI accepts one existing ordinary root-owned release directly under `/var/www/geophysics.ml.fasl-work.com/releases/`, an explicit SHA-256 of `release.json`, and a new absolute evidence directory under `/var/lib/geophysics-deploy/`. It verifies the complete bundle and rejects a current target, an existing `.venv`, an existing evidence destination, group/world-writable input files and unpinned or URL requirements. It installs with the existing `/usr/bin/python3`, repository-local `.venv`, isolated pip, wheel-only resolution and no cache; it never installs a global dependency or builds native code. The complete resolved inventory is retained because direct requirement pins do not lock every transitive dependency.

Installation requires at least4GiB available bytes before mutation, a bounded900second transaction, each process bounded by the remaining transaction time,2GiB address space,240CPUseconds,16MiB captured log ceiling,256MiB per-created-file ceiling and512 file descriptors. Each installer runs in its own process group; timeout/output overflow terminates that group rather than abandoning pip descendants. These are installer controls, not scientific-job admission. Source/web bytes are rehashed after installation. The environment inventory admits only the standard venv interpreter/lib64 links to their measured existing targets; every other link or unexpected node fails. It records ordinary file hashes and interpreter identity with bounded file/byte totals. A successful runtime receipt means only installation and `pip check` passed. Any failure preserves the environment and evidence rather than overwriting or deleting them, and never changes `current`, units, Nginx, accounts or private project data. Actual-host method and service controls remain mandatory.

Private state is outside every release/document root in a dedicated mode0700 service-owned directory. Root-owned mode0600 API environment contains only the required origin, stable auth secret, state path and local account profile. A separate worker environment has storage and individually admitted method flags, never the auth secret. No SMTP is configured. Internal account creation reuses the existing operator CLI with a private file; no embedded owner password or public seed. Existing state is never replaced with a workstation candidate database.

Systemd socket activation supplies exactly one Unix stream socket as fd3 to Uvicorn. Socket mode0660, dedicated service owner and Nginx group restrict access. Nginx overwrites Host, X-Forwarded-Proto and X-Forwarded-For from its own request variables; Uvicorn trusts forwarded headers only on this restricted socket. No TCP backend port or remote API origin is introduced. `/api/` never falls through to `index.html`, never caches responses and does not intercept API errors. Request buffering is disabled for bounded uploads; Nginx's whole-body ceiling permits the declared 200MiB file plus bounded multipart overhead, while application quotas remain authoritative.

API and worker run as a dedicated unprivileged account, read-only code and filesystem except explicit private state, no network access inside their namespaces, no capabilities, no new privileges, limited tasks and swap disabled. API512MiB and worker2GiB are whole-service cgroup ceilings, not claims of per-job hard memory/disk quotas. Worker cgroup shutdown kills descendants; existing job-level counters, cancellation and immutable staging contracts remain separately tested. One worker executes the existing `app.worker` loop. Resource policy does not grant admission to a method whose nominal/upper/malformed/cancellation controls have not passed on the actual host.

## Activation and rollback

The operator stages and validates a new immutable release before changing the active symlink. An exclusive app-specific deploy lock prevents concurrent activation. Required TLS files, current target, source hashes, installed dependency check, measured capacity, schema and service configurations are checked first. There is no automatic certificate bootstrap, DNS change or unrelated service edit. On the first service deployment an absent database may be migrated to the exact current head; an existing database must already be at the reviewed compatible head. Schema-changing releases require a separately reviewed compatibility/migration path; this installer never downgrades or replaces state.

Save the previous app-specific Nginx configuration and current target before switching. Stop API/socket and worker, switch `current` atomically, install only this application's reviewed units and site, run `systemd-analyze verify` and `nginx -t`, then start the socket/API, validate local auth configuration and anonymous project401, and only then start the worker and reload Nginx. Any failure restores the previous current target and site configuration; first deployment restores the legacy static site without claiming a service rollback. Failure after schema change is not silently repaired. Do not overwrite existing staging roots or outputs. Retain the actual command results and failed staging for diagnosis.

After external exact-build verification, actual authenticated user-data workflows and rollback are accepted, retain current plus the two newest qualified rollback releases. Legacy directories are not assumed service-compatible; preserve their original static site configuration for a legacy rollback. Retention is scoped to individually resolved ordinary directories directly under this application's releases root. Never follow links, remove the current target, private storage or another application's directory. Review the exact inventory before removing anything. No generic wildcard recursive cleanup is used.

## Capacity and verification

The read-only host collector uses `statvfs` free bytes available to non-root processes, `/proc/meminfo` MemAvailable and measured regular-file release bytes. Existing releases/project usage is already reflected in free disk. Release-byte measurement is separately bounded to262,144 entries/32GiB and never follows symlinks. Only standard `.venv/bin/python`, `python3`, `python3.12` and `.venv/lib64` links may be skipped, because ordinary Linux virtual environments contain them; every other link is rejected. This is logical regular-file byte measurement, not runtime closure/hash acceptance. Reserve the new archive, extracted source/web, measured API-only environment installation bound, configured1GiB job scratch, API512MiB, worker2GiB and measured controller reserve. No30% whole-host threshold. The exact current and two rollback IDs are explicit operator selections, never invented from a count. Reject unsafe/duplicate/escaping IDs and unexpected filesystem entries. The collector does not delete or activate anything.

The existing read-only HTTPS verifier provides byte and route/API checks, not scientific or browser acceptance. Actual OS service limits/socket permissions, same-origin secure sessions, plural ownership, worker jobs/cancel/restart, concurrent public reading and rollback require real host execution and browser verification. Local injected subprocess fixtures prove ordering/failure behaviour only. Full release acceptance remains refused until those independently recorded SDD requirements are satisfied.
